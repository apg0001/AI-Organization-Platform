# 보안

이 앱은 사용자의 파일과 Claude Code를 다룬다. 로컬 프로그램이라도 보안을 생략하지 않는다.

## 1. 로컬 서버 노출 방지

- 백엔드는 루프백에만 바인딩한다(`AI_ORG_HOST`가 루프백이 아니면 시작 거부). 웹 개발 서버도 `127.0.0.1`.
- `LocalOnlyMiddleware`
  - **Host 허용 목록**(127.0.0.1·localhost·[::1]) — DNS 리바인딩 차단.
  - **Origin 허용 목록**(:3000·:8000) — 다른 웹사이트에서 온 요청(CSRF) 차단. WebSocket도 같은 검사(4403).
  - 상태 변경 요청은 JSON만(업로드 경로만 multipart) — 단순 폼 CSRF 차단.
  - `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- 같은 컴퓨터의 다른 프로세스·다른 OS 사용자는 로그인 없이 API를 쓸 수 없다(§7, 기본 켬).

## 2. 파일 접근

- 프로젝트: 등록된 탐색 경로 안의 실제 경로만. 심볼릭 링크 해석. 루트 등록 금지. 등록 해제는 파일을 지우지 않는다.
- 에이전트 도구: `file_path`·`notebook_path`·`path` 입력이 작업 폴더·첨부 폴더 밖이면 **거부**(읽기 포함, 심볼릭 링크는 실제 경로로 해석).
  Glob의 `pattern`과 Grep의 `glob`도 본다: 글롭 문자가 없는 앞부분을 실제 경로로 풀어(절대 경로·`~`·`..`·심볼릭 링크) 범위 밖이면 거부하고,
  그 뒤에 `..`이나 `..`으로 풀릴 수 있는 조각(`.*`·`.?`·`.{.,}`), 중괄호 안의 `/`·`~`·`..`(`{/etc,x}`)이 있어도 거부한다.
  허용 리스트·auto보다 먼저이고 Claude Code가 되물은 호출에도 똑같이 적용된다. Grep의 `pattern`은 정규식이라 경로로 보지 않는다.
- 컨텍스트 경로: 대화의 프로젝트 안만, 저장·전송 때마다 검증.
- 셸 명령: 인자 중 절대 경로·`~`·`..` 경로가 작업 폴더·첨부 폴더 밖을 가리키면 승인 설정과 관계없이 **사용자 승인**을 받는다
  (명령 이름 자리의 실행 파일과 `/dev/null` 등 장치 파일 제외). 같은 명령 안의 `cd`를 따라 상대 경로 기준을 바꾸고,
  `/status`처럼 한 단계짜리 절대 문자열은 실제로 있는 경로일 때만 경로로 본다(검색어 오탐 방지, #26). 삭제 명령이 범위 밖을 가리키면 삭제가 허용된 에이전트도 승인을 받는다.
  승인 요청에는 이유("작업 폴더 밖 경로를 참조합니다: …")가 함께 보인다.
  상대 경로 인자(`/`가 들었거나 실제로 있는 이름)도 심볼릭 링크를 해석해 범위 밖이면 승인을 받는다(`link/secret`처럼 폴더 안 링크가 밖을 가리키는 경우).
  확장 뒤에 밖을 가리킬 수 있는 인자 — 중괄호 안에 `.`·`/`·`~`가 든 형태(`.{.,}`, `{/etc,x}`), `.`으로 시작하는 글롭 조각(`.*`·`.?`) — 와
  해석할 수 없는 경로(링크 순환 등)는 '밖일 수 있음'으로 보고 승인을 받는다.
- 삭제 판정: `rm`·`rmdir`·`unlink`·`shred`, `git clean`, `find … -delete`. 대소문자를 가리지 않고, `/bin/rm`처럼 경로가 붙은 형태와
  따옴표·백슬래시로 감싼 변형(`'r''m'`, `\rm`)도 삭제로 본다.
- **한계**: 변수 확장(`$HOME/...`), 명령 치환, 스크립트 파일 내부의 경로는 정적으로 알 수 없다. 셸 허용 에이전트는 셸 승인(기본값)을 유지하는 것을 권장한다.
  셸 인자 중 `/`가 없고 실제로 없는 이름은 경로로 보지 않는다.

## 3. 에이전트 권한

- `AgentPermissions`: 셸·파일 쓰기·삭제·네트워크·위임 허용, 승인 필요 묶음(shell·file_write·file_delete·network·delegate·mcp),
  권한 모드(default·acceptEdits·plan·auto), 허용 리스트(`allow_rules`, §3.3). `bypassPermissions`·`dontAsk`는 스키마에서 거부(422).
- 기본값(보수적): 셸 금지, 삭제 금지, 위임 금지(CEO 제외), 셸·파일 쓰기·삭제·MCP 도구는 승인 필요, 모드 default, 허용 리스트 비어 있음.
- 집행 순서: ① 금지 묶음은 `disallowed_tools`(Claude Code deny — 어떤 모드에서도 우선) ② 모든 도구 호출 PreToolUse 훅에서 정책 판정(§3.1)
  ③ Claude Code 자체 확인 요청은 `can_use_tool`. 우리 정책은 Claude Code 권한을 좁히기만 하며 우회하지 않는다
  (훅은 거부하거나 통과시킬 뿐 Claude Code에 `allow`를 돌려주지 않는다).
- `setting_sources=["project"]`: 사용자 전역 설정의 allow 규칙이 앱 승인을 건너뛰지 않게 한다.
- 권한 상속 없음: 각 실행은 그 에이전트 자신의 정책만 쓴다. 위임받은 에이전트도 자기 정책으로 실행한다.
- 실행 중 변경: 권한은 도구 호출마다 DB에서 다시 읽는다('항상 허용'으로 더한 규칙, 실행 중 좁힌 권한이 바로 적용된다).
  권한 모드만은 그 실행이 시작될 때 Claude Code에 넘긴 값을 끝까지 쓴다.
- 위임: 위임 권한이 있는 에이전트만 위임 도구를 받고, 대상은 하위 구성원·협업 대상으로 제한, 순환·깊이(3) 제한.
  `require_approval`에 `delegate`를 넣으면 위임마다 사용자 승인.
- 새 API 경로는 없다. 권한 모드·허용 리스트·'항상 허용'은 로그인으로 보호되는 기존 경로(에이전트 수정, 설계 명세, 승인 결정)의 본문만 넓혔다([API.md](API.md)).

### 3.1 판단 순서(`services/policy.py`의 `decide`)

| 순서 | 조건 | 결과 |
|---|---|---|
| ① | `allow_*`(위임은 `can_delegate`)로 꺼 둔 묶음의 도구 | **거부** |
| ② | 작업 폴더·첨부 폴더 밖 경로 | 파일 도구(`file_path`·`notebook_path`·`path`, Glob `pattern`, Grep `glob`)는 **거부**, 셸 명령이 참조하면 **사용자 승인**(§2) |
| ③ | 허용 리스트 일치(삭제·위임 묶음은 대상 아님) | **허용**(명시적 허용) |
| ④ | 모드가 auto가 아니고 `require_approval`에 든 묶음 | **사용자 승인** |
| ⑤ | 나머지 | 통과 — Claude Code의 판단(권한 모드·자체 규칙)에 맡긴다 |

- ①②는 ③④보다 먼저다. 허용 리스트·auto 모드 어느 쪽으로도 건너뛸 수 없다.
- **auto 모드**에서는 ④를 적용하지 않는다(`require_approval` 값은 저장해 두고, 모드를 내리면 다시 적용된다).
  **삭제·위임 묶음도 예외가 아니다(사양)**: 삭제·위임을 켜 둔 에이전트는 auto에서 묶음별 승인 없이 Claude Code 판단으로 삭제·위임할 수 있다.
  삭제·위임마다 승인을 받으려면 auto를 쓰지 않거나 그 도구를 꺼 둔다.
  대신 Claude Code가 스스로 되물은 호출(`can_use_tool`)은 앱 승인 요청으로 사용자에게 묻는다(사유 "Claude Code가 확인을 요청했습니다.", `source: "runtime"`).
- **명시적 허용과 단순 통과의 구분**: 사용자 승인과 허용 규칙 일치만 '명시적 허용'이다. ⑤의 통과는 '우리 정책이 막지 않음'일 뿐이다.
  default·acceptEdits·plan에서는 훅을 통과한 호출을 Claude Code가 되물으면 다시 묻지 않고 허용한다(기존 동작).
  auto에서는 명시적으로 허용된 호출만 그렇게 하고, 단순 통과한 호출을 Claude Code가 되물으면 사용자에게 묻는다.

### 3.2 지킬 선(어떤 설정으로도 넘을 수 없는 것)

- 작업 폴더 밖 경로는 허용 리스트·auto 모드로 넘길 수 없다(파일 도구 거부, 셸은 매번 사용자 승인. 이 승인은 '항상 허용'으로 만들 수 없다).
- `allow_*`로 꺼 둔 도구는 허용 규칙이 있어도, auto여도 쓸 수 없다.
- 삭제(§2의 삭제 판정)와 위임은 허용 규칙의 대상이 아니다. auto가 아니면 삭제를 허용한 에이전트라도 승인 설정을 따른다.
- 아래 규칙은 저장이 거부된다(422, 사유 메시지 포함 — `services/rules.py`).
  - 셸 전체를 여는 규칙: `Bash`, `Bash()`, `Bash(*)`, `Bash(:*)` 등. `*`는 끝의 `:*`로만 쓸 수 있다.
  - 셸 문법 `&` `|` `;` `$` `` ` `` `>` `<` `(` `)` `{` `}` 줄바꿈이 든 규칙(명령 연결·치환·리다이렉션·변수 확장·묶음).
  - 다른 명령을 대신 실행하는 명령으로 시작하는 규칙: `bash`·`sh`·`zsh`·`dash`·`ksh`·`fish`·`csh`·`tcsh`·`eval`·`exec`·`env`·`xargs`·`su`·`doas`·
    `command`·`builtin`·`nohup`·`time`·`timeout`·`nice`·`watch`. `변수=값`으로 시작하는 규칙.
  - 위험 명령(§3.3 '위험 판정'과 같은 기준 — 저장·매칭·'항상 허용' 생성이 한 함수를 쓴다): `rm`·`rmdir`·`unlink`·`shred`·`sudo`,
    `git`과 `push`가 함께 있는 명령, 삭제 패턴, 셸 이름·`eval`이 어디든 든 명령, `-exec`류 인자, 확장 문법, git 설정·실행 경로 옵션.
  - **접두 규칙(`:*`)으로는 저장할 수 없고 명령 전체 일치로만 저장되는 것**:
    - 인터프리터: python·pypy·node·deno·ruby·perl·php·lua·rscript·tsx·ts-node(버전 숫자 포함).
    - 다른 명령을 실행하거나 파일을 덮어쓸 수 있는 도구: find·fd·sed·awk·gawk·mawk·nawk·tar·zip·ssh·scp·rsync·parallel·tee·dd·mv·cp·ln·install·
      truncate·vi·vim·nvim·emacs·ed·less·more·man·gdb·strace·script·flock·setsid·stdbuf·busybox·tmux·screen·crontab·at.
    - 하위 명령 도구의 단독 접두(`Bash(git:*)`, `Bash(npm:*)`)와 옵션으로 시작하는 접두. 대상 도구: git·npm·pnpm·yarn·npx·bun·bunx·cargo·pip·pip3·
      pipx·uv·poetry·docker·podman·kubectl·helm·make·go·gh·apt·apt-get·brew·systemctl·terraform.
    - 대리 실행 접두: 위 도구의 `run`·`exec`·`dlx`·`x`(`Bash(uv run:*)`, `Bash(docker exec:*)`. `make`는 제외),
      git의 `config`·`submodule`·`bisect`·`rebase`·`filter-branch`·`difftool`·`mergetool`.
      예외로 npm·pnpm·yarn·bun의 `run <스크립트>`는 스크립트 이름까지 적으면 접두로 저장된다(`Bash(npm run build:*)`).
    - 패키지 설치·변경: 패키지 도구(npm·pnpm·yarn·bun·pip·pip3·uv·poetry·cargo·go·gem·brew·apt·apt-get·conda)의 `install`·`i`·`add`·`ci`·
      `update`·`upgrade`·`remove`·`uninstall`·`publish`·`link`·`init` 등(전체 목록은 `rules.py`의 `PACKAGE_SUBCOMMANDS`).
      설치 스크립트가 실행될 수 있어서다(`Bash(npm install:*)`, `Bash(pip install:*)` 거부).
    - 패키지 실행 도구(npx·bunx·pipx)로 인터프리터·셸·대리 실행 명령·위 '실행 가능 도구'를 부르는 접두(`Bash(npx tsx:*)`, 버전 표기 `tsx@latest` 포함).
      그 밖의 패키지 접두(`Bash(npx vitest:*)`)는 사람이 직접 저장할 수 있다 — 그 패키지에 주는 임의 인자를 허용한다는 뜻이다(§3.5).
  - `/`·`~`로 시작하거나 `..`·`\`가 든 파일 규칙, 위임 도구(`mcp__org__*`), 지원하지 않는 도구 이름, 괄호가 붙은 `WebSearch`·`WebFetch`·MCP 규칙.
- 상한: 에이전트당 규칙 50개, 규칙 하나 200자.
- 이미 저장돼 있던 규칙이 지금 검증에 걸리면 **그 규칙만** 무시하고(서버 경고 로그) 실행·조회는 계속한다(`schemas.stored_permissions`).
  나머지 권한은 저장된 그대로 적용된다. 무시하는 쪽은 항상 '더 묻는' 쪽이다.
- 설계 담당 AI의 권한 확대 제안은 바로 반영되지 않고 `permission_suggestion`으로 남아 사용자가 수락해야 적용된다.
  확대로 보는 것: 꺼진 `allow_*`·`can_delegate` 켜기(금지 → 허용), `require_approval`에서 묶음 빼기, 권한 모드 상향
  (plan < default < acceptEdits < auto — plan → default 포함), 허용 규칙 추가, 작업 범위(`file_scope`) 확대.
  저장이 거부되는 규칙이 든 제안은 명세 검증에서 실패해 **그 턴의 제안 전체가 반영되지 않는다**(설계 대화에 오류로 표시).
  설계 담당 지침에도 auto 전환·규칙 추가를 하지 말라고 적혀 있지만, 막는 것은 지침이 아니라 위 서버 검사다.
  허용 목록(Skills·MCP·Plugins)은 AI가 바꿀 수 없다.

### 3.3 허용 리스트(`allow_rules`)

Claude Code 규칙 문법 중 이 앱이 안전하게 판정할 수 있는 부분만 지원한다. 일치하면 승인을 묻지 않는다(§3.1 ③). 애매하면 '불일치'로 보고 평소대로 묻는다.

| 규칙 | 뜻 |
|---|---|
| `Bash(접두:*)` | 명령이 접두와 같거나 `접두 + 공백`으로 시작(단어 경계 — `Bash(npm test:*)`는 `npm testx`에 맞지 않는다) |
| `Bash(명령 전체)` | 공백을 정리한 명령과 정확히 일치 |
| `Read(글롭)` | Read·Grep·Glob의 경로 |
| `Edit(글롭)`·`Write(글롭)` | 쓰기 도구 묶음(Edit·MultiEdit·Write·NotebookEdit)의 경로. 둘은 같은 뜻이다 |
| `WebSearch`·`WebFetch`·`mcp__서버__도구` | 그 도구(괄호 없이 이름만) |

매칭 규칙:
- 복합 명령(`&&`·`||`·`;`·`|`·`&`)은 조각으로 나누어 **모든 조각**이 규칙에 맞아야 한다. 따옴표를 해석하지 않고 나누므로 틀려도 묻는 쪽으로만 틀린다.
- 명령에 `$`·`` ` ``·`<`·`>`·줄바꿈이 있으면(변수 확장·치환·리다이렉션) 규칙과 대조하지 않는다 = 불일치.
- **위험 판정**(조각마다, 규칙이 맞아도 불일치로 본다). 따옴표·백슬래시를 지우고 소문자로 바꾼 뒤 공백과 `=`·`:`·`,`로 나눈 단어(경로는 이름만)로 본다.
  - `rm`·`rmdir`·`unlink`·`shred`·`sudo`가 있거나 `git`과 `push`가 함께 있음, 삭제 패턴(§2).
  - 셸 이름(bash·sh·zsh·dash·ksh·fish·csh·tcsh)·`eval`이 인자·따옴표 안을 포함해 어디든 있음(`sh -c …`).
  - `-exec`·`-execdir`·`-ok`·`-okdir`·`-delete` 인자.
  - 확장 문법 `{` `}` `*` `?` `[` `]` `(` `)`, 단어 첫머리(또는 `=`·`:` 뒤)의 `~`. `HEAD~1`의 `~`는 확장이 아니다.
  - git: `git` 바로 뒤가 옵션이거나 `-c`·`-C`가 있음, `--config-env`·`--exec-path`·`--exec`·`--extcmd`·`--upload-pack`·`--receive-pack`·`--output`(파일을 쓴다)으로
    시작하는 옵션, `alias.` 문자열.
  - `변수=값`으로 시작하는 조각.
- 파일 글롭은 **작업 폴더 기준 상대 경로**다. `**`는 여러 폴더, `*`·`?`는 한 경로 조각 안에서만 일치하고 `폴더/**`는 그 폴더 자신도 포함한다.
  대상은 심볼릭 링크를 해석한 실제 경로로 본다. 첨부 폴더의 파일에는 파일 규칙이 적용되지 않는다.
  Glob `pattern`·Grep `glob`이 작업 폴더 밖을 가리킬 수 있으면 불일치다.
- 저장된 뒤 기준이 엄격해져 더는 유효하지 않은 규칙은 무시한다(= 묻는다, §3.2).

### 3.4 프리셋과 권한 표(웹)

값의 원본은 `apps/web/src/lib/permissions.ts`다. 서버에는 프리셋 개념이 없고, 웹이 아래 값으로 에이전트 권한을 저장한다.

| 칸 상태 | `allow_*` | `require_approval` |
|---|---|---|
| 허용 | true | 그 묶음 없음 |
| 승인 필요 | true | 그 묶음 있음 |
| 금지 | false | 그 묶음 있음(다시 켜도 승인부터 받게) |

MCP는 `allow_*` 필드가 없어 허용·승인 필요 두 상태뿐이다(서버를 쓸 수 있는지는 에이전트의 '허용된 MCP 서버' `allowed_mcp_servers`로 정한다). 위임 칸은 `can_delegate`에 대응한다.

화면: 조직 화면의 '권한' 탭에 권한 표가 있다(행 = 에이전트, 열 = 모드·셸·파일 수정·삭제·네트워크·위임·MCP·허용 규칙 수). 칸을 누르면
허용 → 승인 필요 → 금지 순서로 바뀌고(MCP는 허용 ↔ 승인 필요) 바로 저장한다. 저장된 칸 값과 실제 동작이 다른 두 경우는 칸 아래에 따로 적는다:
셸이 금지면 삭제는 칸 값과 관계없이 막히고('셸 금지로 막힘'), auto에서는 '승인 필요'가 적용되지 않는다('auto: Claude 판단').

| 프리셋 | 모드 | 셸 | 파일 수정 | 삭제 | 네트워크 | MCP |
|---|---|---|---|---|---|---|
| 안전(읽기만) | default | 금지 | 금지 | 금지 | 금지 | 승인 필요 |
| 표준(편집·셸 승인) | default | 승인 필요 | 승인 필요 | 금지 | 허용 | 승인 필요 |
| 자율(auto) | auto | 승인 필요 | 승인 필요 | 바꾸지 않음 | 허용 | 승인 필요 |

- 어느 프리셋도 위임, 작업 범위(`file_scope`), 허용 리스트를 바꾸지 않는다. 자율 프리셋의 '승인 필요' 칸은 auto인 동안 적용되지 않고(Claude 판단) 모드를 내리면 다시 적용된다.
- 프리셋은 권한 표 위의 버튼(선택한 에이전트·부서·전체에 한꺼번에)과 운영 조직도 노드의 메뉴(우클릭, 컨텍스트 메뉴 키·Shift+F10, 노드의 메뉴 버튼)로 적용한다.
  설계 화면의 조직도에는 이 메뉴가 없다.
- **확인 창**('권한을 넓힐까요?'): 저장된 값이 아니라 **실제 동작**이 넓어질 때 뜬다 — 묶음별로 금지 < 승인 필요 < Claude 판단 < 허용 순서에서 올라가는 경우,
  모드 상향(plan < default < acceptEdits < auto), 전에 없던 허용 규칙 추가. 그래서 셸을 켜서 막혀 있던 삭제가 풀리는 경우와 auto 전환으로
  '승인 필요'가 Claude 판단이 되는 경우도 잡는다. 권한 표·커맨드 센터 권한 팝오버·조직도 프리셋 메뉴·에이전트 상세의 설정 편집이 같은 절차
  (`usePermissionChange`)를 쓴다. 설계 화면의 초안 편집에는 확인 창이 없다(초안은 '검토 후 적용' 단계를 따로 거친다).
  이 확인은 웹 화면의 절차이고, 서버 API는 로그인한 사용자의 권한 변경을 그대로 받는다.
- 저장: 기존 에이전트 `PATCH`. 웹은 화면이 보던 값이 아니라 캐시의 최신 값 위에 바뀐 항목만 다시 얹어 저장하고, 저장 뒤 다시 불러올 때까지
  권한 표·권한 팝오버·에이전트 설정의 권한 영역을 잠근다. 잠금 중에 들어온 변경은 저장하지 않고, 반영되지 않았다는 토스트로 알린다.
- 조직도 배지: `auto`(auto 모드) / `계획만`(plan 모드) / `승인 필요`(그 밖의 모드에서 실제로 승인을 거치는 묶음이 있음) / `셸 금지`. 앞의 셋은 하나만 보인다.
- 커맨드 센터 권한 팝오버는 실행 패널의 '승인 대기' 카드와 '실행 중' 목록의 에이전트 이름에서 열린다(모드·묶음 칸 변경, 허용 규칙 요약, 전체 편집 링크).

### 3.5 한계

- `Bash(npm run build:*)`·`Bash(make build:*)`처럼 스크립트를 실행하는 규칙은 그 스크립트가 하는 일까지 허용한다. 스크립트 내용은 검사하지 않는다.
  접두 뒤의 인자도 막지 않는다: `Bash(make build:*)`는 `make build CC=…`도 통과시킨다.
- 접두 저장 거부 목록(§3.2)은 알려진 도구의 목록이다. 목록에 없는 도구는 접두 규칙으로 저장할 수 있고, 그 도구가 다른 명령을 실행할 수 있는지는 검사하지 않는다.
  사람이 직접 저장한 `Bash(npx vitest:*)` 같은 패키지 접두는 그 패키지의 임의 인자를 허용한다.
- 작업 폴더 안에 미리 파일을 써 두어야 악용할 수 있는 실행 경로는 규칙 일치로 통과할 수 있다: `npm test --script-shell=…`, `pytest -p 플러그인`,
  `git diff --ext-diff` 등. 파일 쓰기 승인과 함께 봐야 한다.
- 반대로 판정이 엄격해 정상 명령도 다시 묻는 경우가 있다: `pytest …::t[1]`(`[`가 확장 문법), `git log --grep=push`(`git`과 `push`가 함께 있음) 등.
- 여러 창에서 동시에 권한을 바꾸면, `PATCH`가 권한 전체를 보내므로 짧은 틈에 한쪽 변경이 덮어써질 수 있다(후속 이슈로 남김).
- 변수 확장·명령 치환이 든 명령은 규칙에 맞지 않을 뿐(묻는다), 승인하면 그 내용은 알 수 없다. 스크립트 내부 경로도 알 수 없다(§2).
- Bash 규칙은 `Bash` 도구에만 적용된다. 같은 셸 묶음의 BashOutput·KillShell·KillBash·Monitor에는 맞는 규칙 종류가 없다.
- 위험 판정은 넓게 잡는다: `git`과 `push`가 한 명령에 함께 있으면 `git push`가 아니어도(예: `git stash push`) 항상 묻고, 인자에 `sh`·`rm` 같은 단어가 있어도 묻는다.
- auto에서는 삭제·위임 묶음에도 묶음별 승인이 적용되지 않는다(§3.1, 사양).
- 권한 저장에는 버전 필드가 없다. 클라이언트가 오래된 권한 전체를 `PATCH`하면 그 사이 '항상 허용'으로 추가된 규칙이 덮어써질 수 있다
  (웹은 최신 값 위에 다시 얹어 저장해 이를 줄인다. API를 직접 쓰는 클라이언트는 해당 없음).
- **실제 Claude Code의 auto 동작은 미검증**이다. 다음은 가짜 런타임과 SDK 콜백을 흉내 낸 자동 테스트로만 확인했다:
  PreToolUse 훅이 auto 분류기보다 먼저 불리는지, 분류기가 막을 때 `can_use_tool`로 되묻는지, auto 모드를 지원하는 CLI 버전.

## 4. 명령 실행 승인

승인 요청에는 에이전트, 도구, 대상(명령·경로, 최대 300자), 사유, 출처(`hook`·`runtime`), '항상 허용' 때 추가될 규칙이 보인다.
시간 제한(기본 900초) 후·실행 종료·중지 시 거부/만료. 승인·거부는 DB(`approvals`)와 활동 기록에 남는다.

### 4.1 항상 허용

승인하면서 그 요청으로 만든 규칙을 **그 에이전트**의 허용 리스트에 더한다. 추가될 규칙은 승인 요청을 만들 때 미리 계산해 화면에 보인다.

| 요청 | 만들어지는 규칙 |
|---|---|
| 셸 명령(기본) | **명령 전체 일치**: `ls -la` → `Bash(ls -la)` |
| 하위 명령 도구(§3.2의 목록, npx·bunx·pipx 제외)의 `<도구> <하위 명령> …` | 두 단어 접두: `git status -s` → `Bash(git status:*)`, `npm test` → `Bash(npm test:*)`, `make build` → `Bash(make build:*)` |
| `npm`·`pnpm`·`yarn`·`bun`의 `run <스크립트>` | 세 단어 접두: `npm run build` → `Bash(npm run build:*)` |
| 인터프리터, 대리 실행(`uv run …`, `docker exec …`, `git rebase …` 등 §3.2에서 접두가 거부되는 것), 패키지 실행 도구(npx·bunx·pipx — 패키지와 무관하게 항상), 패키지 설치·변경(`npm install …`, `pip install …`), 하위 명령이 없거나 옵션으로 시작하는 경우 | 명령 전체 일치 |
| 파일 도구(경로가 있을 때) | 작업 폴더 기준 상대 경로 그대로: 읽기는 `Read(경로)`, 쓰기는 `Edit(경로)` |
| WebSearch·WebFetch·MCP 도구 | 도구 이름 |

- **규칙을 만들지 않고 이번만 허용하는 경우**(승인 요청에 사유 `always_reason`이 함께 오고, 화면의 '항상 허용' 버튼은 꺼진다):
  삭제·위임 요청, 작업 폴더 밖 경로를 참조하는 요청, 복합 명령·치환·리다이렉션이 든 명령, `변수=값`으로 시작하는 명령,
  §3.3의 위험 판정에 걸리는 명령(`sudo`·`git push`, `git -C …`, `ls *.py` 같은 확장 문법, `find … -exec` 등),
  저장이 거부되는 규칙이 되는 경우(§3.2), 경로를 지정하지 않은 파일 도구 요청(경로 없는 Grep·Glob — 작업 폴더 전체를 여는 `Read(**)`를 자동으로 만들지 않는다),
  경로에 `*`·`?`가 든 파일, 규칙 종류가 없는 도구, 규칙이 이미 50개인 경우.
- 승인 요청의 버튼은 거부 · 권한 보기(그 에이전트의 설정 탭 `/agents/{id}?tab=settings`) · 이번만 허용 · 항상 허용이다. '항상 허용' 옆에 추가될 규칙이 글자로 보인다.
- 도구의 원본 입력은 DB에 저장하지 않는다. 승인을 기다리는 동안 메모리에만 두고, `approvals.detail`에는 도구·짧은 대상·사유·규칙만 남긴다.
- 규칙은 에이전트 단위다. 대화·프로젝트 단위가 아니므로 **그 에이전트가 다른 프로젝트 대화에서 일할 때도 적용된다**
  (파일 규칙은 그때의 작업 폴더 기준 상대 경로로 해석된다).
- 규칙을 더하면 활동 기록 `agent.rule_added`가 남고, 같은 실행의 다음 도구 호출부터 바로 적용된다.

## 5. 민감 정보

- 이 앱은 Claude 자격증명·API 키를 저장하지 않는다. 예외로 **사용자가 사용량 화면에서 'Claude 사용량 조회'를 켠 경우에만**
  Claude Code CLI 로그인 토큰을 읽어 Anthropic 사용량 API(`api.anthropic.com`) 요청 헤더에 쓴다. 토큰은 메모리에서만 쓰고
  DB·로그·응답에 남기지 않으며 갱신하지 않는다([USAGE.md](USAGE.md)). 이 기능 말고는 앱이 외부로 요청을 보내지 않는다.
- MCP 설정의 env·헤더·인자·URL 쿼리 값은 응답에 넣지 않는다. 허용된 서버의 원본 설정(비밀 포함)은 실행 옵션으로만 Claude Code에
  전달하고 DB·로그·화면에 남기지 않는다(테스트 `test_run_request_carries_allowed_mcp_and_plugins`). Git 원격 URL의 자격증명은 지운다.
- 실행 기록에는 도구 이름과 짧은 대상만 저장한다(도구 출력 원문 저장 안 함). 대화 본문과 응답은 로컬 DB에 저장된다.
- 데이터 폴더 `~/.ai-org`는 0700, 첨부 파일은 0600.
- 데스크톱 앱: 요약 API(`/api/v1/desktop/*`)는 앱이 시작할 때 만든 임의 토큰(128비트×2)으로만 열린다. 토큰은 앱과 백엔드의 메모리·
  환경 변수에만 있고 저장하지 않는다. 토큰이 없으면(브라우저 실행) 이 경로는 404다. 앱 창은 원격 주소(127.0.0.1)라 Tauri IPC가 없다.
- 알림 본문에는 에이전트 이름, 도구·대상(80자), 응답 앞부분(120자)이 들어간다. 잠금 화면에 알림 내용이 보일 수 있으니 OS 알림 설정을 확인한다.

| 시도 제한 | 아이디별 연속 실패 5회부터 1초·2초·4초… 최대 5분 대기(429). 없는 아이디도 같은 비용으로 검증 |
| 비밀번호 변경 | 현재 비밀번호 확인 후 변경, 다른 브라우저 세션은 끊는다 |
| 계정 초기화 | `apps/server/.venv/bin/ai-org-admin reset-auth` — 계정·세션만 지운다(조직·대화 유지) |
| 끄기 | `AI_ORG_AUTH=off`(테스트·단일 사용자 전용 컴퓨터). 끄면 루프백·Host·Origin 검사만 남는다 |
| 분리 | 앱 로그인과 Claude Code 인증은 별개다. 에이전트는 CLI에 로그인된 Claude Code를 쓴다 |

**Planned(다중 사용자)**: `memberships(user, organization, role)`, 조직·프로젝트·대화 조회에 소유 범위 적용, 사용자별 대화 기록,
`AuthProvider` 확장으로 OAuth(GitHub/Google, 상태값·PKCE). 현재 데이터 모델의 조직·대화에는 소유자 열이 없다.
