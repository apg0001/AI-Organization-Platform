# 에이전트 오케스트레이션

구현: `services/runs.py`(`delegation_targets`, `_org_tools`, `_delegate`), `services/prompting.py`(위임 안내),
`runtime/claude_code.py`(인프로세스 MCP 서버 `org`), `services/policy.py`(`delegate` 묶음).

## 1. 흐름

```
사용자 → CEO ──delegate_task──▶ 부서장 ──delegate_task──▶ 담당자
          ▲                         ▲                         │
          └──────── 보고(도구 결과) ─┴──────── 보고(도구 결과) ─┘
CEO가 보고를 검토·취합해 사용자에게 최종 보고
```

| 대화 대상 | 받는 에이전트 | 비고 |
|---|---|---|
| 조직 전체 | CEO(is_lead) | 조직 구성 전체를 받고 업무를 나눠 위임·취합 |
| 팀 | 부서 대표(상위 관리자가 부서 밖인 첫 구성원) | 팀원 목록을 받고 팀을 대표 |
| 에이전트·`@멘션` | 그 에이전트 | 각자 병렬 실행(동시 실행 한도 내) |
| `@All` | CEO | 조직 전체 공지로 표시 |
| `/delegate @이름 업무` | 그 에이전트 | 사용자가 직접 위임(작업 기록) |

## 2. 위임 도구(에이전트가 쓰는 도구)

위임 권한(`permissions.can_delegate`)이 있는 에이전트의 실행에만 인프로세스 MCP 서버 `org`가 붙는다(도구 이름 `mcp__org__*`).

| 도구 | 인자 | 동작 |
|---|---|---|
| `delegate_task` | assignee(이름), title, brief | 작업(Task) 생성 → 대상 에이전트를 같은 대화에서 실행 → 끝나면 그 보고를 도구 결과로 돌려줌 |
| `request_review` | reviewer(이름), content | 검토 작업(`검토: …`) 생성 → 검토 의견을 도구 결과로 돌려줌 |
| `run_plan` | tasks[{key, assignee, title, brief, depends_on[], review_by?}] (최대 12) | 작업 계획을 한 번에 실행하고 작업별 결과를 돌려줌(아래 §2-1) |

- **대상 규칙**: 보고 트리의 모든 하위 구성원 + 이 에이전트가 협업 관계로 연결한 대상(활성만). 그 밖은 거부하고 가능한 대상을 알려 준다.
- **순환·깊이**: 위임 체인에 이미 있는 에이전트에게는 다시 위임할 수 없다. 체인 깊이 3을 넘으면 도구를 주지 않는다.
- **같은 대화 중복**: 대상이 이 대화에서 이미 실행 중이면 거부(같은 세션 동시 resume 방지).
- **병렬**: 서로 다른 대상에게 여러 번 호출하면 함께 진행된다.
- **교착 방지**: 위임 결과를 기다리는 동안 위임자는 동시 실행 슬롯을 반납했다가 결과가 오면 다시 얻는다
  (테스트: 동시 실행 한도 1에서도 완료).
- **권한**: 도구 호출은 `delegate` 묶음으로 판정한다. `require_approval`에 `delegate`를 넣으면 위임마다 사용자 승인을 받는다.
  위임받은 에이전트는 **자기 권한**으로 실행된다(권한 상속 없음).
- **프롬프트**: 위임 가능 에이전트의 시스템 프롬프트에 위임 대상 목록과 사용 지침(목표·범위·결과물 형식 명시, 받은 보고 검토·취합,
  간단한 일은 직접)이 들어간다. 위임받은 에이전트는 `[위임자(직책)의 위임] … 보고하는 형식으로 정리` 머리글을 받는다.

## 2-1. 작업 계획(`run_plan`)

1. **검증**: key 중복, 위임할 수 없는 담당자·검토자, 담당자=검토자, 없는 선행 작업, 순환(`a → b → a`)을 거부하고 이유를 돌려준다.
2. **실행**: 선행 작업이 모두 끝난 작업부터 시작한다. 독립 작업은 함께 진행하되, 같은 에이전트는 담당자별 잠금으로 한 번에 하나만
   실행한다(같은 대화의 세션 동시 이어쓰기 방지). 위임자는 계획이 끝날 때까지 동시 실행 슬롯을 반납한다.
3. **결과 전달**: 뒤 작업의 지시에 `[선행 작업 결과]`(작업별 최대 2000자)를 붙인다. 검토 요청에도 같은 지시를 붙인다.
4. **검토·재작업**: `review_by`가 있으면 결과물을 검토자에게 보낸다. 검토자는 첫 줄을 `[승인]` 또는 `[수정 요청]`으로 시작한다.
   수정 요청이면 검토 의견을 붙여 담당자에게 재작업을 맡긴다(최대 2회). 그래도 승인되지 않으면 작업 상태를 `review`(사람 검토 필요)로 둔다.
5. **실패 전파**: 선행 작업이 실패·취소되면 뒤 작업은 실행하지 않고 `cancelled`로 둔다.
6. **보고**: 작업별 상태(완료·실패·취소·검토 미승인)와 결과 발췌를 위임자에게 돌려준다. 작업은 `depends_on`에 선행 작업 ID를 기록한다.

## 3. 기록과 표시

- `Task`: `parent_id`(위임자의 작업), `assignee_id`, `requested_by_id`, `status`(running → done·failed·cancelled), `result`.
- 위임받은 실행은 같은 대화의 assistant 메시지(`data.delegated_by`, `task_id`)로 남고 화면에 "← 위임자의 위임"으로 표시된다.
- 활동 기록 `task.delegated`·`task.review`, WebSocket `task.delegated`. 실행 패널 작업 목록은 위임 트리로 들여 쓴다.
- 위임 중인 에이전트의 활동은 `delegating`(사무실 머리 위 "📨 위임 중").

## 4. 실패·중지

- 위임받은 실행이 실패·중지되면 위임자에게 그 상태와 오류가 보고로 돌아가고, 위임자가 재시도·재배정·사용자 보고를 결정한다.
- `/stop`(또는 중지 버튼)은 그 대화의 모든 실행(위임 포함)을 중지한다.
- 서버 재시작 시 진행 중 작업은 `failed`로 정리된다.

## 5. 실측(2026-11-25, Claude Code 2.1.326, Raspberry Pi)

소프트웨어 개발 조직 CEO에게 "QA 엔지니어와 백엔드 개발자에게 각각 한 문장 질문을 위임하고 취합해 보고"
→ `delegate_task` 2회(백엔드는 설계자 아래 간접 하위) → 두 에이전트가 같은 대화에서 보고 → CEO가 취합(전체 21초, 작업 2건 done).

실측 2(2026-11-25): CEO가 `run_plan`으로 "기획 → (기획 결과를 받아) API 목록, 코드 리뷰어 검토" 계획 실행 → 리뷰어 [수정 요청](4개 지적)
→ 백엔드 재작업 → [승인] → CEO 취합(52초, 작업 4건 done). 이때 검토 요청에 선행 결과가 빠진 문제를 발견해 고쳤다.
